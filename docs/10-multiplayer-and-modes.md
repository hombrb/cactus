# 10 — Multiplayer and Session Modes

Deliberately short. The application is out of scope; what belongs here is only what
the *logic* forces on the deployment: who owns the truth, how a snap race is
arbitrated, and what a shared-device game must do that a networked one need not.

---

## 1. Two modes, one engine

| | **Room** | **Hotseat** |
|---|---|---|
| Devices | one per player | one, shared |
| Identity | join code, no account | none |
| Authority | server process | the device |
| Projection driven by | socket identity | an `activeViewer` pointer |
| Snap | on | off (`hotseat` preset, [07 §8](07-snap.md)) |
| Turn timeouts | on | off |

The reducer is **identical**. Everything that differs is either a `RuleConfig` key
or a question of who calls `projectFor`.

## 2. Rooms

- **Join code**: 6 characters from an unambiguous alphabet (no `O`/`0`, `I`/`1`).
  Generated by the server, rejected on collision, case-insensitive.
- **No accounts.** A player is a `playerId` + display name. The `playerId` and a
  rejoin token live in the client's `localStorage`; that pair is the only identity.
- **Host** = first joiner. Owns `StartMatch` and `StartNextRound`
  ([05](05-engine-core.md)). If the host leaves, promote the next connected player
  — never block the room on one person's tab.
- **Lifetime**: a room is created on demand and destroyed after a TTL of
  inactivity. Rooms are ephemeral by nature; there is nothing here worth keeping
  once everyone has gone home.

## 3. Authority

**Server-authoritative, always.**

```
client                     authority
  |  Action  ------------------>|
  |                             |  validate(state, action)
  |                             |  (state, events) = applyAction(state, action)
  |<---- projectEvent(e, you) --|  fan out, per-recipient projection (09)
```

- The client may run `validate` locally for instant feedback (grey out an illegal
  slot), and may render an optimistic animation. It **never** owns state and must
  reconcile to the projected events.
- The client never holds enough state to cheat: it does not have the stock, the
  seed, or opponents' faces ([09](09-hidden-information.md)).
- Actions carry `playerId`; the authority overwrites it with the identity of the
  connection that sent it. A client asserting somebody else's id is a dropped
  connection, not a rejected action.

### Hosting, given "no database"

The engine needs a **single writer per room** holding `GameState` in memory. That
constraint — not persistence — is what picks the deployment:

| Option | Fits? | Notes |
|---|---|---|
| **A. One long-lived process** — Node + WebSocket, or PHP via Workerman/Ratchet, on any small host | **recommended** | Rooms are a `Map<code, GameState>` in RAM. Zero persistence, zero schema. A restart drops in-flight games; with a TTL of minutes and rounds of minutes, that is an acceptable failure mode. |
| **B. Host-browser authority** + a thin relay (WebRTC / PeerJS) | true zero-backend | No server state at all. Dies with the host's tab, and the host's client holds the full `GameState` — meaning the host *can* cheat. Fine for friends, not for strangers. |
| **C. Vercel serverless + ephemeral KV** (Upstash and similar) | works, but | Serverless functions are stateless, so every action becomes read-modify-write against the KV, with a lock or a compare-and-set on `actionCounter`. Smallest ops burden, but the KV *is* a database, which was the thing to avoid. |

**Recommendation: A.** It is the only option that is simultaneously honest about
state, cheap, and free of a datastore. Note that plain Vercel *without* any store
cannot host option A — serverless functions have no shared memory — so "Vercel and
no DB" resolves to option B or C, and B is the interesting one.

Whichever is chosen, the reducer does not change. That is the point of keeping it
pure.

## 4. Reconnection

- Rejoin with `(roomCode, playerId, rejoinToken)`.
- The server marks `connected = true`, emits `ConnectionChanged`, sends
  `projectFor(state, playerId)` and the projected event log from the client's last
  acknowledged index.
- Replay policy for peeks that happened while away: see
  [09 §6](09-hidden-information.md#6-reconnection). Default is full replay.
- While a player is disconnected, their turn still comes round. `Timeout` fires
  after `cfg.timing.turnTimeoutMs` and plays the neutral move
  ([05 §8](05-engine-core.md#8-timeouts)) — never an announcement.
- A player who never returns is skipped by `advanceTurn` only if `eliminated`;
  disconnection alone does not remove them, because they may come back. Rooms with
  everybody gone die by TTL.

## 5. Snap fairness

This is the only place where real time enters the system, and it lives **outside**
the reducer ([07 §1](07-snap.md#1-two-mechanisms-kept-apart)).

The authority buffers, orders, then submits:

```
on receive Snap(playerId, target, forVersion) at serverTime t:
  if forVersion != state.discardVersion:
    submit immediately                       // stale: the reducer decides (07 §4.3)
    return

  if no open buffer for forVersion:
    open buffer B(forVersion), closing at t + cfg.timing.snapGraceMs
  B.add({ playerId, target, adjusted: t - oneWayLatency(playerId) })

on buffer B closes:
  sort B.entries by adjusted, then by playerId          // deterministic tiebreak
  submit each entry to the reducer in that order
```

- `oneWayLatency(playerId)` is half the smoothed ping RTT the server already tracks
  for its heartbeat. It is an estimate, and it is allowed to be wrong — it only
  reorders players who clicked within `snapGraceMs` (250 ms) of each other.
- **Set `snapGraceMs = 0` to disable all of it** and let raw packet arrival decide.
  That is a legitimate choice; it just means the player on fibre always wins.
- Only the *first* submitted entry can succeed. Every later one arrives at a
  reducer whose `discardVersion` has already advanced, and is handled as a lost
  race — `NONE` (silent) or `AS_FAILED_SNAP` per `cfg.snap.loserPenalty`.
- The 250 ms delay is imperceptible against the ~1 s reaction time the mechanic
  actually tests.

The reducer never sees a timestamp. The **action log**, which records the submitted
order, remains the complete replay input.

## 6. Single-device hotseat

Two players, one phone, opponent's half rotated 180°. The engine is unchanged; the
whole problem is **preventing the two humans from seeing each other's private
information on a screen they share**.

Three mechanisms, all client-side, all mandatory:

1. **`activeViewer` replaces socket identity.** `projectFor(state, activeViewer)`
   is called with whoever is currently entitled to look. Everything private — the
   initial peek, a drawn card, a `CardRevealed` — is rendered only for
   `activeViewer`.

2. **A hand-off gate between turns.** `TURN_END` is not a 3-second window here; it
   is a full-screen "pass the phone to Bob — tap when ready" panel. Nothing private
   is on screen while it is up. This is precisely why `EndTurn` exists as an
   explicit action ([03 §6](03-domain-model.md#6-actions)): the window closes when
   a human confirms, not when a timer expires. `cfg.timing.endOfTurnWindowMs` and
   `turnTimeoutMs` are both `null` in the `hotseat` preset.

3. **The masked band.** With the opponent's layout drawn upside-down at the top and
   yours at the bottom, the shared middle strip (stock, discard, held card) is the
   leak. Mask it while a private reveal is on screen, and never render a
   `CardRevealed` face in the shared band — put it over the owner's own half.

Consequences worth stating plainly:

- **Snap is off** ([07 §8](07-snap.md#8-hotseat)). One pair of hands, one device:
  there is no race to arbitrate, only an arm-speed contest the engine cannot see.
- **The initial peek is sequential, not simultaneous.** Each player peeks behind
  the hand-off gate in turn. The `INITIAL_PEEK` barrier already tolerates this — it
  waits for `hasPeeked` on everyone and does not care about wall-clock ordering
  ([05 §4](05-engine-core.md#4-the-initial-peek-barrier)).
- **Trust is physical.** Nothing stops a player from watching over a shoulder. The
  mode is for two people who want to play, not for strangers.

## 7. What is intentionally left undecided

Framework, transport encoding, rendering, animation, styling, storage of finished
matches, matchmaking, and anything resembling accounts. None of it affects the
rules, and fixing it here would date this document faster than the game changes.
