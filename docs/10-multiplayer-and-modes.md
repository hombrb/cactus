# 10 — Multiplayer and Session Modes

Deliberately short. The application is out of scope; what belongs here is only what
the *logic* forces on the deployment: who owns the truth, how a snap race is
arbitrated, and what a shared-device game must do that a networked one need not.

---

## 1. Two modes, one engine

| | **Room** | **Flat table** |
|---|---|---|
| Devices | one per player | one, lying between two players |
| Identity | join code, no account | none |
| Authority | server process | the device |
| Projection driven by | socket identity | one `projectFor` per half, both live |
| Snap | on | on, ordered by `pointerdown` ([07 §8](07-snap.md#8-two-players-on-one-device)) |
| Turn timeouts | on | off |

The reducer is **identical**. Everything that differs is either a `RuleConfig` key
or a question of who calls `projectFor`.

## 2. Rooms

- **Join code**: 6 characters from an unambiguous alphabet (no `O`/`0`, `I`/`1`).
  Generated by the server, rejected on collision, case-insensitive.
- **No accounts.** A player is a `playerId` + display name, and the `playerId`
  *is* the credential: whoever presents it to a room is given that seat. It is
  therefore minted from `crypto.randomUUID`, kept in `localStorage`, and never
  shown, logged, or put in a join link. An earlier version of this section also
  called for a separate rejoin token; with an unguessable id that token is a
  second copy of the same secret, so there is deliberately only one.
- **Host** = first joiner. Owns `StartMatch` and `StartNextRound`
  ([05](05-engine-core.md)). If the host leaves, `LobbyLeave` promotes the next
  connected, non-eliminated player in seating order and emits `HostChanged` —
  never block the room on one person's tab. When nobody is left to promote the
  departed host stays nominal, and the room dies by TTL.
- **Lifetime**: a room is created on demand and destroyed after a TTL of
  inactivity. Rooms are ephemeral by nature; there is nothing here worth keeping
  once everyone has gone home.

## 3. Authority

**Server-authoritative, always.**

```
client                     authority
  |  Action  ------------------>|
  |                             |  validate(state, action)
  |                             |  (state, events) = applyAction(state, action)
  |<---- projectEvent(e, you) --|  fan out, per-recipient projection (09)
```

- The client may run `validate` locally for instant feedback (grey out an illegal
  slot), and may render an optimistic animation. It **never** owns state and must
  reconcile to the projected events.
- The client never holds enough state to cheat: it does not have the stock, the
  seed, or opponents' faces ([09](09-hidden-information.md)).
- Actions carry `playerId`; the authority overwrites it with the identity of the
  connection that sent it. A client asserting somebody else's id is a dropped
  connection, not a rejected action.

### Hosting, given "no database"

The engine needs a **single writer per room** holding `GameState` in memory. That
constraint — not persistence — is what picks the deployment.

**Decided: Cloudflare Workers + Durable Objects, free plan.** One room is one
Durable Object, which *is* the single writer, addressed by `idFromName(code)` —
so the join code is the address and there is no room registry to keep. The built
PWA is served by the same Worker, so the game and its authority share an origin.

The alternatives, recorded so they are not re-litigated:

| Option | Verdict |
|---|---|
| **One long-lived process** — Node + WebSocket on a small host | Works, and was the original recommendation. Rejected only because it needs a host that is paid for and kept alive; a Durable Object is the same architecture without the machine. |
| **Host-browser authority** + a thin relay (WebRTC / PeerJS) | True zero-backend, but dies with the host's tab, and the host's client holds the whole `GameState` — meaning the host *can* cheat. |
| **Vercel serverless + ephemeral KV** | Functions are stateless, so a no-DB room needs an external store anyway, and every action becomes read-modify-write with a compare-and-set on `actionCounter`. The KV *is* the database this was meant to avoid. |
| **Hostinger shared hosting** | Cannot host the authority at all: no long-lived process, no WebSocket. It can serve `dist/` and hold the domain. |

The numbers that make the free plan sufficient: Durable Objects have been on the
Workers **free** plan since April 2025 (SQLite backend only — hence
`new_sqlite_classes` in `wrangler.toml`, not `new_classes`), with 100 000
requests/day and 5 GB of storage. Inbound WebSocket messages bill at **20:1**,
outbound are free; a four-player match is roughly 1 000 inbound messages, so
about 50 billable requests. The daily quota is therefore something like 1 800
matches.

**The one trap.** WebSocket Hibernation evicts the object from memory while the
sockets stay open, so in-memory `GameState` is simply gone. The object must
persist after every action, and per-socket identity must ride on the socket's own
attachment rather than in a `Map`. This is affordable because `GameState` is
fully JSON-serialisable — every `Set`/`Map` in the engine is local to a function
body — and that property is asserted by a test rather than assumed.

Whichever is chosen, the reducer does not change. That is the point of keeping it
pure: `worker/room.ts` owns sockets, storage and the alarm clock, and no game
logic at all, while everything that decides what happens lives in
`src/net/room-core.ts` where it can be tested on a fake clock with no workerd.

## 4. Reconnection

- Rejoin with `(roomCode, playerId, rejoinToken)`.
- The server marks `connected = true`, emits `ConnectionChanged`, sends
  `projectFor(state, playerId)` and the projected event log from the client's last
  acknowledged index.
- Replay policy for peeks that happened while away: see
  [09 §6](09-hidden-information.md#6-reconnection). Default is full replay.
- While a player is disconnected, their turn still comes round. `Timeout` fires
  after `cfg.timing.turnTimeoutMs` and plays the neutral move
  ([05 §8](05-engine-core.md#8-timeouts)) — never an announcement.
- A player who never returns is skipped by `advanceTurn` only if `eliminated`;
  disconnection alone does not remove them, because they may come back. Rooms with
  everybody gone die by TTL.

## 5. Snap fairness

This is the only place where real time enters the system, and it lives **outside**
the reducer ([07 §1](07-snap.md#1-two-mechanisms-kept-apart)).

The authority buffers, orders, then submits:

```
on receive Snap(playerId, target, forVersion) at serverTime t:
  if forVersion != state.discardVersion:
    submit immediately                       // stale: the reducer decides (07 §4.3)
    return

  if no open buffer for forVersion:
    open buffer B(forVersion), closing at t + cfg.timing.snapGraceMs
  B.add({ playerId, target, adjusted: t - oneWayLatency(playerId) })

on buffer B closes:
  sort B.entries by adjusted, then by playerId          // deterministic tiebreak
  submit each entry to the reducer in that order
```

- `oneWayLatency(playerId)` is half the smoothed ping RTT the server already tracks
  for its heartbeat. It is an estimate, and it is allowed to be wrong — it only
  reorders players who clicked within `snapGraceMs` (250 ms) of each other.
- **Set `snapGraceMs = 0` to disable all of it** and let raw packet arrival decide.
  That is a legitimate choice; it just means the player on fibre always wins.
- Only the *first* submitted entry can succeed. Every later one arrives at a
  reducer whose `discardVersion` has already advanced, and is handled as a lost
  race — `NONE` (silent) or `AS_FAILED_SNAP` per `cfg.snap.loserPenalty`.
- The 250 ms delay is imperceptible against the ~1 s reaction time the mechanic
  actually tests.

The reducer never sees a timestamp. The **action log**, which records the submitted
order, remains the complete replay input.

## 6. Two players, one phone (flat table)

The phone lies **flat on the table between the two players**, portrait. Each
player sits at one end; the opponent's half is rotated 180° so both read their own
end the right way up. Stock and discard sit in the band between them. This is the
arrangement the `table2p` preset ([02](02-rule-config.md)) and the V1 app assume.

> **This supersedes an earlier "pass the phone" design** in which one
> `activeViewer` held the device at a time and a full-screen hand-off panel
> covered every turn change. Both models are viable, but they are not
> interchangeable: passing the phone forces snap off and makes the initial peek
> sequential, while the flat table keeps both halves live and both mechanics
> intact. Everything below assumes the flat table.

The engine is unchanged. Both halves are rendered in the same pass from **two
different `projectFor` calls**, so the top half is structurally incapable of
drawing what only the bottom player may see.

### Privacy is by moment, not by turn

Both halves are live the whole time, so there is no hand-off gate to hide behind.
Instead each *private moment* is hidden individually, and the rule is one gesture:

| Gesture | Meaning |
|---|---|
| **Tap** | Place the held card here · choose a power target |
| **Long-press** | Reveal a card you are entitled to see — hidden again on release |
| **Swipe toward the middle** | Snap ([07 §8](07-snap.md#8-two-players-on-one-device)) |

Long-press is what makes this work physically: you cup the phone with the same
hand that is holding the card down, and nothing can be left exposed by accident.

Three placement rules follow, and all three are load-bearing:

1. **A card is drawn in the half of the player entitled to see it.** A
   `CardRevealed` naming an *opponent's* slot is rendered in the **actor's own
   tray**, never lit up in the opponent's half — the actor could not shield it
   there.
2. **The middle band carries no text.** Anything written between the two players
   is upside down for one of them. Only the stock back and the discard face.
3. **Card faces print rank and suit in two opposite corners, the second rotated
   180°** — exactly like a real playing card. This is what makes the shared
   discard legible from both ends, and it is the single most important design
   detail on the screen.

### `projectFor` permits; the client still decides

`knownBy` persists, so a card peeked at the start of the round stays *permitted*
for the rest of it. On a shared screen, rendering everything the projection allows
would leave both players' peeked cards face up for anyone to lean over and read.

So a face is drawn only when **both** hold: the projection permits it, **and** an
explicit single-use **reveal grant** exists. Grants are created by the rules event
that entitled the player to look (`InitialPeeked`, `CardRevealed`) and are consumed
the moment they stop looking. You get one look, as at a real table. This is the
concrete form of the rule in
[09 §5](09-hidden-information.md#5-what-the-engine-deliberately-does-not-model).

### Consequences

- **Snap stays on.** Both players can reach their own half at all times, so the
  race is genuine. Ordered by `pointerdown`, not by gesture recognition.
- **The initial peek is simultaneous.** Each player long-presses their own two
  nearest cards, at their own end, at the same time. The `INITIAL_PEEK` barrier
  already tolerates any ordering
  ([05 §4](05-engine-core.md#4-the-initial-peek-barrier)).
- **`EndTurn` is still explicit**, and `cfg.timing.endOfTurnWindowMs` is `null`:
  the end-of-turn window closes when a human presses the button, never on a timer.
- **Trust is physical.** Nothing stops a player from leaning over. The mode is for
  two people who want to play, not for strangers.

## 7. What is intentionally left undecided

Framework, transport encoding, rendering, animation, styling, storage of finished
matches, matchmaking, and anything resembling accounts. None of it affects the
rules, and fixing it here would date this document faster than the game changes.
